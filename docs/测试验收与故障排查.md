# 测试验收与故障排查

本文是当前版本的最终验收手册，给出从源码回归、ESP-IDF 构建、USB 烧录到真板验收的唯一执行顺序。所有“通过”结论都必须来自当前提交、当前构建目录和当前真板。

## 1. 当前产品合同

当前版本必须同时满足以下规则：

1. 固定右手腕佩戴。
2. 一次会话只做一种主动作；用户要换动作时先停止，再开始新会话。
3. 首次稳定识别出的 `selected_action` 是本轮显示、计数器和摘要的主动作。
4. 主动作确认后的 `inferred_action` 只用于诊断；休息、静坐、低置信度或其它类别噪声不得切换主动作。
5. 对次数和步数动作，休息或数据质量不合格时冻结并清除未完成半周期；恢复原动作后必须从一个新完整周期继续。`sit` 在 `RUNNING` 的合法单调 tick 中累计时长，`PAUSE` 或 `STOP` 后停止。
6. 10 次或 10 步的验收范围为 8～12。允许误差不代表允许批量跳数、休息后补数或错误动作增数。
7. 手表没有振动马达。协议保留位固定为零，软件验收和真板验收均不得设置振动测试项。
8. 当前固件源码启用 `APP_BENCH_ALWAYS_ON=true`：屏幕自动熄灭、Light-sleep 和 Deep-sleep 暂时关闭，开发者诊断门只在 RAM 中打开。该事实只适用于当前常亮联调镜像，不能写成量产低功耗已经通过。
9. 当前 BLE 联调 PIN 固定为 `123456`，仍要求加密、认证和绑定。固定 PIN 只用于现场联调，不能作为量产安全设计。

算法、业务状态和协议的详细定义分别见：

- [算法原理、训练与实时计数](算法原理、训练与实时计数.md)
- [系统架构与业务流程](系统架构与业务流程.md)
- [BLE 通信、设备配置与会话存储](BLE通信、设备配置与会话存储.md)
- [硬件平台、手表界面与低功耗](硬件平台、手表界面与低功耗.md)

## 3. 测试金字塔

发布必须从下往上执行。低层失败时停止，不进入更高层。

| 层级 | 验证对象 | 通过门 | 失败动作 |
|---:|---|---|---|
| L0 | 文本、清单和生成物哈希 | 清单 SHA-256 与生产工件一致；`git diff --check` 通过 | 修源码或文档，不构建 |
| L1 | Python 297 维特征、双 M0、累计策略 | 冻结验证记录满足特征误差 `≤1e-4`、logits/累计误差 `≤1e-3` 且类别索引一致 | 禁止更新 C 头或固件 |
| L2 | ESP32 领域、协议、传感器替身和状态机 | 十二组主机测试均输出 `HOST_TEST_PASS`；总标志 `HOST_TESTS_OK count=12` | 禁止 ESP-IDF 发布构建 |
| L3 | Windows 上位机、BLE 协议、会话补传 | Release 构建和全部 C# 测试退出码 0 | 禁止发布上位机或 BLE 固件 |
| L4 | ESP32-S3 真正编译与链接 | ESP-IDF 5.5.4、目标 `esp32s3`；BIN 时间属于本次构建；分区未溢出 | 本次构建未产出有效 BIN 时禁止烧录 |
| L5 | 四段 Flash 与启动 | 精确目标 USB；四个地址正确；四次片上 Hash 校验；硬复位后稳定启动 | 重烧或回退，不做动作测试 |
| L6 | 真板 UI、触摸、BLE、分类与计数 | 本文第 8 节全部满足 | 保留日志和 CSV，按故障树定位 |

主机替身不能证明真实面板、触摸、射频、I2C、电池、电流或任务调度已经通过。

## 4. 软件发布门

### 4.1 环境预检

从仓库根执行：

```powershell
$ErrorActionPreference = 'Stop'

if (-not (Test-Path -LiteralPath '.venv\Scripts\python.exe')) {
    throw '缺少项目 Python 环境：.venv\Scripts\python.exe'
}

if (-not (Test-Path -LiteralPath '.codex-local\cache\esp-idf-v5.5.4\tools\idf.py')) {
    throw '缺少项目本地 ESP-IDF 5.5.4'
}

if (-not (Test-Path -LiteralPath '.codex-local\cache\espressif-tools')) {
    throw '缺少项目本地 ESP-IDF 工具链'
}

git status --short --branch
git diff --check
```

`git status` 用于确认当前提交和待交付差异。工作树可以有本次明确范围内的改动，但不得混入数据集、构建缓存、本地发布包或未知文件。

### 4.2 定向快速门

只修改固件或文档时，可先运行定向检查以快速定位：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File `
  esp32\host_tests\run_all.ps1 -StopOnFailure

dotnet build pc\FitnessCoach.sln -c Release

git diff --check
```

定向门只用于开发反馈，不能替代发布前全量门。

### 4.3 完整发布顺序

1. 核对双 M0 manifest、便携包和两份 C 头的 SHA-256。
2. 运行 ESP32 十二组主机测试。
3. 构建 `pc/FitnessCoach.sln` 的 Release 配置。
4. 使用 `esp32/firmware/tools/idf_project.ps1 -Action build` 完成 ESP-IDF 真编译和链接。
5. 读取本次 BIN、分区表、四段地址和完整 SHA-256。
6. 在精确 USB 目标上完成四段烧录与四次片上 Hash 校验。
7. 最后执行真板 UI、触摸、BLE、分类、计数和长稳验收。

软件构建成功不代表真板通过；没有当前硬件证据时，发布记录必须明确写为“硬件未验证”。

## 5. 构建产物审计

全量门通过后重新读取当前构建结果：

```powershell
$firmwareBuild = Resolve-Path 'esp32\firmware\build'
$appBin = Join-Path $firmwareBuild 'imu_fitness_handheld.bin'
$flashArgs = Join-Path $firmwareBuild 'flash_args'

Get-Item -LiteralPath $appBin |
    Select-Object FullName, Length, LastWriteTime

Get-FileHash -Algorithm SHA256 -LiteralPath $appBin

Get-Content -LiteralPath $flashArgs
```

验收要求：

1. BIN 的修改时间属于本次构建。
2. SHA-256 在发布记录中保存完整 64 位十六进制值。
3. `flash_args` 必须包含同一构建目录的四段：

| 地址 | 镜像 | 作用 |
|---:|---|---|
| `0x0` | `bootloader/bootloader.bin` | 二级启动程序 |
| `0x8000` | `partition_table/partition-table.bin` | 32 MiB Flash 分区表 |
| `0x10000` | `ota_data_initial.bin` | 初始 OTA 选择数据 |
| `0x30000` | `imu_fitness_handheld.bin` | 当前应用 |

4. 分区表的 `factory` 槽从 `0x30000` 开始、大小为 `0x400000`；应用不得越界。
5. 文档不得固定记录镜像大小或 SHA；每次都以当前命令输出为准。

## 6. USB 身份、四段烧录与证据

### 6.1 只选择目标设备

```powershell
$targets = @(
    Get-CimInstance Win32_PnPEntity |
        Where-Object {
            ($_.PNPDeviceID -match 'VID_303A&PID_1001') -and
            ($_.Name -match '\(COM\d+\)')
        }
)

if ($targets.Count -ne 1) {
    throw "目标 ESP32-S3 USB 设备数量不是 1，实际=$($targets.Count)"
}

$targets | Select-Object Name, PNPDeviceID

if ($targets[0].Name -notmatch '\((COM\d+)\)') {
    throw '无法从目标设备名称解析 COM 端口'
}

$port = $Matches[1]
$port
```

禁止按“第一个 COM 口”猜设备，禁止访问其它串口或共享 USB 设备。

### 6.2 保存正式发布证据

```powershell
$releaseId = Get-Date -Format 'yyyyMMdd-HHmmss'
$evidenceDir = Join-Path 'docs\results\releases' $releaseId
New-Item -ItemType Directory -Force -Path $evidenceDir | Out-Null

$flashLog = Join-Path $evidenceDir 'flash.log'
$appHash = Get-FileHash -Algorithm SHA256 `
    -LiteralPath 'esp32\firmware\build\imu_fitness_handheld.bin'
$appHash | Format-List | Out-File `
    -LiteralPath (Join-Path $evidenceDir 'application-sha256.txt') `
    -Encoding utf8
Get-Content -LiteralPath 'esp32\firmware\build\flash_args' |
    Out-File -LiteralPath (Join-Path $evidenceDir 'flash-args.txt') `
    -Encoding utf8

& powershell.exe -NoProfile -ExecutionPolicy Bypass -File `
    esp32\firmware\tools\idf_project.ps1 `
    -Action flash `
    -Port $port 2>&1 |
    Tee-Object -FilePath $flashLog

$flashExit = $LASTEXITCODE
if ($flashExit -ne 0) {
    throw "烧录失败，exit=$flashExit"
}

$verifiedCount = @(
    Select-String -LiteralPath $flashLog `
        -SimpleMatch 'Hash of data verified'
).Count
if ($verifiedCount -ne 4) {
    throw "片上 Hash 校验次数应为 4，实际=$verifiedCount"
}
```

只有以下事实同时成立才算烧录通过：

- USB 身份精确匹配 `VID_303A&PID_1001`；
- 本次应用 SHA 与发布记录一致；
- 地址为 `0x0 / 0x8000 / 0x10000 / 0x30000`；
- 四段均出现 `Hash of data verified`；
- 工具执行硬复位；
- 没有并行运行第二个 esptool。

发布证据由当前提交重新生成，并随对应 GitHub Release 一起归档；构建缓存、本机绝对路径和临时脚本不得混入文档目录。

### 6.3 烧录后观察

先观察 USB 端口至少 30 秒，确认没有反复消失和重枚举。随后启动监视器：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File `
  esp32\firmware\tools\idf_project.ps1 `
  -Action monitor `
  -Port $port
```

使用 `Ctrl+]` 退出。需要记录：

- `reset_reason`；
- 当前常亮联调模式标记；
- QMI8658、AXP2101、PCF85063 初始化结果；
- `BLE_HEAP before_start free=... largest=...`；
- `BLE_WORKER_STACK minimum_free_bytes=...`；
- 是否进入 HOME 或稳定错误页。

## 7. 启动与故障码

当前完整启动顺序：

```text
NVS 与设备配置
  -> 队列、锁与推理 PM 锁
  -> Waveshare BSP、AMOLED、触摸与 LVGL
  -> BOOT / SELF_TEST 可见页面
  -> QMI8658、AXP2101、PCF85063
  -> LittleFS 与会话恢复
  -> 协调器、IMU 流水线与双 M0
  -> NimBLE 与可连接广播
  -> 业务任务
  -> HOME
```

| 画面/故障码 | 含义 | 首查证据 | 处理 |
|---|---|---|---|
| 无画面 | BSP、面板、供电或 LVGL 创建早于可见错误页失败 | 串口最早日志；官方 Demo A/B | 不改业务状态机，先恢复厂家显示基线 |
| `1001` | QMI8658、AXP2101 或 PCF85063 关键初始化失败 | I2C 地址、WHO_AM_I、供电、板型 | 核对控制器与总线，不绕过自检 |
| `1002` | LittleFS/会话仓储不能安全挂载或恢复 | 分区表、挂载日志、双槽文件 | 恢复存储；不能把失败伪装成空会话仓储 |
| `1003` | 协调器、IMU 流水线或模型领域初始化失败 | 模型 manifest、类别/特征合同、领域日志 | 恢复同一组模型工件，重跑 L1～L4 |
| `1004` | BLE 启动后无法为完整业务任务分配栈 | `BLE_HEAP`、最大连续片内块、任务创建结果 | 查片内堆碎片和栈边界；禁止只隐藏错误页 |
| 停在 SELF_TEST | 某初始化未返回或任务死锁 | 最后一条串口日志、任务状态 | 定位阻塞调用；不要延长自检动画掩盖 |

`1004` 的当前处理是停在稳定错误页。若设备实际反复重启，说明故障发生在该保护之前或存在其它复位源，必须读取 `reset_reason`。

## 8. 真板回归

### 8.1 显示、触摸与设置

1. HOME 连续显示 30 秒，文字边缘无重影、圆角安全区无遮挡。
2. 连续进入和退出设置页 20 次，不得卡页或失去触摸。
3. 设置页必须同时可见“亮度、诊断、忘记电脑、返回”四个按钮，按钮区不得滚动。
4. 亮度按 `15% -> 35% -> 60% -> 100% -> 15%` 循环；每次松手后页面仍停留在设置页并显示新值。
5. “返回”必须回到 HOME，不能依赖上下拖动或重启。
6. 连续完成至少 20 轮“开始 -> 运动/休息 -> 停止 -> 完成 -> HOME”；全程触摸可用，页面不冻结。
7. 当前常亮联调镜像不验收自动熄屏、Light-sleep 或 Deep-sleep；这些功能必须在关闭 `APP_BENCH_ALWAYS_ON` 后另立版本验收。

### 8.2 BLE 配对、重连与忘记设备

新设备首次连接：

1. 上位机重新扫描，选择名称以 `BPNN-FIT-` 开头的设备。
2. 点击快速连接。
3. Windows 自定义配对按当前联调合同提交 PIN `123456`；手表显示配对状态。
4. 连接成功后读取 Manifest、LiveState 和 Battery Service。
5. 断开再连接 10 次，必须回到同一设备，不能误连附近其它 BLE。

忘记设备必须区分两端：

- 上位机“忘记设备”：取消 Windows 配对并清除应用固定设备 ID；
- 手表“忘记电脑”：删除 NimBLE 保存的电脑绑定并断开当前链路。

Windows 与手表保存的绑定不一致时，必须两端都忘记后重新扫描。只清一端会留下不一致密钥，常见表现是“能扫描到但 Windows BLE 配对失败”。不要连续点击连接覆盖第一条失败原因。

至少执行一次一小时连接测试，记录 RSSI、重连次数、最后错误、BLE worker 最小剩余栈和内部堆趋势。

### 8.3 分类与计数冒烟门

先验收用户当前重点六类：

1. 开合跳 10 次；
2. 深蹲 10 次；
3. 跳跃深蹲 10 次；
4. 跳跃弓步 10 次；
5. 挥手 10 次，来回为一次；
6. 步行 10 步。

每类至少做 5 个独立会话。每轮严格执行：

1. 右手佩戴；
2. 点击开始；
3. 只做该轮真值动作；
4. 正常速度完成 10 次或 10 步；
5. 中途站立或静坐休息 5 秒；
6. 恢复同一动作；
7. 停止并完成；
8. 导出 44 列中文 IMU CSV。

每轮通过门：

- 稳定动作与人工真值一致；
- 正常两窗约 2.96 秒确认，最迟四窗约 3.92 秒；超过该范围必须查看分类窗口和质量位；
- 主动作一旦确定，本轮显示名称不因休息或噪声变化；
- 每个完整周期只增加 1，手表和上位机依次显示中间整数，不得延迟后一次性补跳；
- 每个设备 EventV1 到达后，手表和上位机必须在下一次人工动作开始前显示新累计；
- 休息 5 秒期间累计值完全不变；
- 恢复动作后不能把休息前半周期和休息后半周期拼成一次；
- 最终累计为 8～12；
- 停止后累计不再增加。

冒烟门通过后，对全部 11 类执行同样流程，并增加慢速、正常速度、较小幅度和自然个体差异。不得只用某一次真板日志调阈值后再把同一日志当验证结果。

验证集没有逐次人工计数标注时，只能证明分类、活动门和相位覆盖，不能宣称计数误差满足 ±2。

### 8.4 日志证据

44 列 CSV 至少包含：

- 设备单调时间与上位机接收时间；
- `gx、gy、gz、ax、ay、az` 六轴和质量位；
- 会话序号、右手腕、设备状态和稳定动作；
- 基础 M0、掩码 M0、融合类别与置信度；
- 分类窗口序号、结束时间、推理耗时和失败累计；
- EventV1 计数事件序号、动作、增量、累计和原始设备时刻。

分类列只能向前关联同会话已完成窗口；计数标记必须使用设备事件原始时间，不能用 BLE 到达时间伪造。

## 9. 失败决策树

```text
软件门失败？
  是 -> 处理对应层；不构建、不烧录
  否
    ESP-IDF 新 BIN 或分区失败？
      是 -> 处理构建；禁止烧录
      否
        USB 身份不是唯一目标？
          是 -> 停止；确认 VID/PID 与端口
          否
            四次 Hash 不完整？
              是 -> 本次 Flash 失败；重新烧录或回退
              否
                无画面/故障码？
                  是 -> 按第 7 节定位
                  否
                    BLE 或触摸失败？
                      是 -> 保留串口、PC 日志和当前哈希；按第 10 节定位
                      否
                        分类/计数失败？
                          是 -> 导出 44 列 CSV；离线重放后再改算法
                          否 -> 当前版本真板门通过
```

## 10. 常见故障排查

### 10.1 能扫描到但连接失败

1. 记录上位机第一条完整错误，不反复点击。
2. 确认选中的是 `BPNN-FIT-*`，不是附近其它 BLE。
3. 在上位机忘记设备。
4. 在手表设置页忘记电脑。
5. 必要时在 Windows 蓝牙设置中删除对应设备。
6. 重启手表，重新扫描并建立新绑定。
7. 仍失败时保存 PC 日志、手表串口中的 GAP/ENC_CHANGE、安全启动结果和当前固件 SHA。

Windows 已经开始恢复绑定时，NimBLE 返回 `EALREADY` 表示同一安全流程正在进行，不是新的致命错误。若当前源码仍把它当失败，源码合同应首先失败。

### 10.2 设置页缺少亮度或无法返回

当前 UI 合同固定四宫格且禁止按钮容器滚动。若真板只看见“诊断、忘记电脑”：

1. 对照当前应用 SHA，确认真板运行的固件与本次发布工件一致；
2. 检查 `ui_lvgl_renderer.c` 的设置页四宫格、亮度按钮和返回按钮仍由同一固定布局创建；
3. 检查触摸坐标是否与 410×502 旋转方向一致；
4. 检查 `ui_lvgl_renderer.c` 是否仍使用绝对四宫格、移除 `LV_OBJ_FLAG_SCROLLABLE` 并把滚动偏移归零；
5. 不得用增加页面高度或要求用户拖动规避布局错误。

### 10.3 多轮训练后页面卡住

先区分三类：

- COM 端口消失后重现：整机复位、掉电或 USB 重枚举；
- COM 仍在且串口继续输出：UI 任务、LVGL 锁、触摸分派或业务队列故障；
- COM 仍在但串口也停止：任务死锁、看门狗前阻塞或内存破坏。

记录 `reset_reason`、最后页面、最后一次触摸、内部堆、最大连续块、应用 owner 栈和 BLE worker 栈水位。禁止只增加任务栈掩盖过大的内联栈帧；源码合同要求大路径保留非内联边界。

### 10.4 点击开始后重启或冻结

1. 查看 `reset_reason` 是否为看门狗、软件复位或异常。
2. 运行十二组主机测试与固件源码合同。
3. 检查应用 owner 任务的静态最深调用链和运行时高水位。
4. 检查分类、计数、effects 和协调器候选副本是否同时放入栈。
5. 候选镜像通过栈审计、ESP-IDF 链接和四段 Hash 后才能烧录。

### 10.5 识别正确但计数延迟或批量跳数

1. 用 CSV 的分类窗口末点确认首次稳定动作时间；
2. 用 EventV1 原始设备毫秒确认计数器何时产生事件；
3. 比较手表显示、BLE 事件和上位机更新时间；
4. 若 EventV1 已逐次产生而 UI 批量更新，修 UI/BLE 队列；
5. 若 EventV1 本身晚到，重放相位和活动门；
6. 若准备期前几个周期没有事件，检查准备缓存、IMU gap/reset 和锁类前回放；
7. 不得仅降低一个阈值来拟合单次日志。

### 10.6 休息时继续加数

检查顺序：

1. 休息窗是否被活动门判为静止；
2. 质量位是否允许计数；
3. 冻结时是否清除了半周期；
4. `selected_action` 是否保持不变；
5. 主动作确认后的异类 `inferred_action` 是否只写诊断；
6. 停止事务后是否还有未消费的 EventV1 排队。

恢复目标是“休息冻结同一主动作计数器”，不是切换成“静坐若干次”，也不是强制把实时噪声伪装成主动作。

## 11. 当前限制

当前发布必须明确保留以下限制：

1. 模型佩戴域为右手腕；左手腕不属于当前验收范围。
2. 一次会话只支持一种主动作；切换动作必须结束会话。
3. 当前 `APP_BENCH_ALWAYS_ON=true`，自动熄屏、Light-sleep 和 Deep-sleep 不属于本次发布验收。
4. 固定 PIN `123456` 只用于联调，不是量产安全方案。
5. 手表没有振动马达；软件不得把振动列为反馈或验收项。
6. 10 次或 10 步允许 8～12，但逐次显示、休息冻结和停止后不增数仍是硬门。
7. `dual_m0_manifest.json` 的硬件验证状态只有在本次真板门完成后才能更新；软件门不能替代真板验证。
